# The lifecycle model

The method comes from poteto's statechart skill in the pstack plugin (https://github.com/cursor/plugins/tree/main/pstack/skills/statechart): a TLA+ model of a system that moves between states, checked with TLC, drawn as a Mermaid statechart, with the shortest path to each state that breaks a rule.

`Lifecycle.tla` models the task-attempt lifecycle of `scripts/run.py` as it is in this version of the plugin: 0.21.0. Its lifecycle is that of 0.19.0 (PR-1 of #97, its merge gate, #100, and the transition table, #99, on top of 0.18.0 at ff2c8b0, PR #87); 0.20.0 (#104, #106, #107) changes briefs, worker rules, the compaction hook, hints, and how `record` reads a done task's phase (below), and no state, action or rule of the model; 0.21.0 (#111) adds `run.py repoint`, which the model leaves out and which changes no state, action or rule of it (see "0.21.0: repoint"). It reads the code, not the docs: what `record` prints as `next:`, what each command refuses, what each command writes. Its purpose is to find dead ends (a state where the hinted command is refused or useless and nothing else moves) and lost transitions before an operator does. Line numbers in the model and in this file are of `scripts/run.py` at that version; keep them current when the code moves. The phase changes need none: a test checks them against the model (see "Phase edges").

The model found the six issues that 0.12.0 fixes (#56, #57, #58, #59, #61, #62). Their old paths live on as sensitivity checks (`REGRESS_*`), below. 0.12.1 adds the ghost row (#65), see "Ghost rows". 0.19.0 makes a closed task wait in progress for its merge, see "0.19.0". 0.18.0 adds the verifier's finding labels, the refusals of a broken role file and of a read-only `info/exclude`, and the no-change close of 0.12.3; see "0.18.0" and "Open breaks".

## How to read the model

- The Manager's only moves are the command that `record` names in its `next:` hint, and `record` itself. `Hint` is a derived operator: what `record` would print from the current state. `Record` is an action only when `record` writes something (a row, a meta, a `claude stop`); while it would, `Hint = "record"` and no other command is enabled.
- A refused command (exit 2) is not enabled. A command that would change nothing is not enabled either. `Done` is the only self-loop, for the end states (merged, or abandoned). So TLC's deadlock check is the rule "no dead end".
- Hints that name no run.py command (`tg add ... --type decision`, "record later", "merge it on the host", "reopen it") are `"none"`: the Manager waits for the world to move. The `unknown` hint (`claude logs <sid>; if it has stopped working, run.py stop ...`) is read as `stop`: the Manager looks, finds the session has stopped working, and stops it.
- At the last attempt the retry hints say `run.py abandon <id> <mode> (the cap is 3 attempts), or run.py launch <id> --attempt <n+1> to override`. The Manager never overrides, so the hint is `abandon`. The at-cap `unknown` hint offers `run.py stop ..., then ... launch --attempt` as its second alternative; the model reads abandon there too, so in 0.12.0 a recovery stop at the cap happens only when the Manager chooses that override (`regress-59.cfg` reads that branch on purpose). A pause at the cap under a recorded verify-failed verdict gets an abandon hint from `unclosed_next` (the pause is exempt, the verdict is not): a quirk, not a break.
- Two hints are read, not copied: `unclosed_next` for check-only ("verify --again for a stronger verdict, or accept it") maps to `verify --again`; verify-blocked is left out (it acts like check-only in every modelled decision).
- Sessions keep their state until something acts on them. An idle verifier may wake up or go quiet (30 minutes, `VERIFIER_QUIET_MINUTES`); an idle worker, and every quiet, blocked, prompted, failed or finished session, changes only when a command stops it. A worker files one result per attempt, as its last step (worker.md), and its row may stay live for a while after that.
- A stop is `run.py stop`. Under a STOP first line in the standing orders (`Orders.stop`, 542-549) it is a pause (`Reason: pause`) and does not use an attempt; without one it recovers a session that went quiet or broke (`Reason: recover`) and counts toward the cap, as DIED does (5686-5694, #59). `close` stops the worker with `Reason: close` (5303-5323). `commit_stopped` copies the reason into the row it files (3675-3677). The Manager runs `stop` where the `unknown` hint says so (#58); the operator runs it as a pause.
- A ghost row (#65, `Session.ghost`, 590): a live row with no status and no pid, no process now. Young, it is `unknown` for `record` (the hint names `run.py stop`), and the CLI may start it again. `claude stop` keeps a row's state and removes its status and pid (a probe on CLI 2.1.318, 2026-11-06): a busy row becomes "stopped", a done/idle row "done" with no status, both finished; an idle/working row (one that said it will check back) becomes working with no status and no pid, a young ghost. The field saw exactly that: `close --verdict verify-failed` stopped an idle worker, and the next `launch` refused on the row "None/working" (2026-11-06). Since part 3 of #65 every stop that run.py runs goes through `stop_session` (624-637), which notes the id in the run directory's `stopped-sessions` file (`STOPPED_FILE`, 221), and `Run.sessions` (491-500) counts a noted live row with no status as finished at once. So in the model a run.py stop always ends the row (`AfterStop`), whatever it was; the field's case (an idle/working worker with its result filed, stopped by launch's stopped-idle) no longer blocks the launch. Before part 3 (`REGRESS_65B`) a stopped idle/working row stayed a young ghost until its 30 quiet minutes: the model's `ghostStopped`, which does not come back (the probe saw a stopped busy row stay stopped and never saw a stopped row revive; only a kill-induced ghost came back). A stop the operator runs by hand is not modelled. After `VERIFIER_QUIET_MINUTES` (30) with no transcript write and no start (`quiet_for`, 3612-3620, above `verifier_over`), `Run.sessions` (491-500) marks it finished (`finished`, `turn_over` set; `live`, `stuck`, `unknown` cleared): launch no longer waits for it, record salvages its report or files DIED, a verifier goes to `lost_verifier`, and cleanup removes it. The model has two values: `ghost` (young: live, unknown) and `ghostGone` (quiet: finished). The `ghost` flag is line 590.
- The operator's free moves (write a STOP order, lift it, order a pause) are behind `OPERATOR_PAUSES`. With them on, every state has a step out (order, pause, lift, launch), so TLC's deadlock check would find nothing: the check configs keep them off, so that "no dead end" means "following record's hints leads out". `pause.cfg` turns them on to check the pause flow itself. A STOP order also refuses launches (2335-2337, exit 3) and holds merges (5616-5617, 5625-5628, 5072).
- 0.18.0 faults (`FAULTS`, off in the check configs, on in `faults.cfg` and `faults-pr.cfg`): once per run the role file of the task breaks (`fault = "role"`) or `info/exclude` turns read-only (`fault = "exclude"`); the operator's repair (`OperatorRepairs`) is enabled only in a broken state, so it is not a free exit from every dead end, and a fault happens once (`faulted`) so that a repaired copy of a dead end is still a dead end. See "0.18.0 refusals".

## What the model leaves out

- `wait` and `notify-to`: `wait` polls and writes nothing; the notify line only wakes the Manager, which then runs `record`. Neither changes the state the model reads.
- Other tasks, decisions (`waits_for`, `gated`, `answered`), dependencies, slots and `check_cap`, `adopt`, `status`, `roles`, `cleanup` (it never stops a live session; since 0.18.0 it does not delete a session's scratch folder either). Of the standing orders only the STOP first line is in (`stopOrder`); a MERGE: line is always present.
- Messages (0.16.0: `ask`, `answer`, `steer`, `inbox`, the doorbell, the resume): `mailbox/Mailbox.tla` models them. In this model a worker never asks and the Manager never steers, so `cmd_launch`'s open-ask refusal (2388-2399), `cmd_stop`'s parked-asker and rowless cases (5671-5683) and record's `holds` (3759-3779) never arise. 0.18.0's one change there, `resume_with` catching an `ignore_scratch` refusal and settling the row as pending (3153-3157), is noted under "0.18.0 refusals".
- The re-plan at the cap (0.18.0 rule 13, manager.md "Spent attempt cap", run.md): the Manager abandons and plans a new task (a design task, a split, a closed checklist). A new task is another instance of this model, so the model ends at `Abandon`; it does not draw a step from Abandoned back to Not started. The `--attempt` override the rule allows for a bounded fix is left out as before: the Manager never overrides here.
- The worker's `check-report` refusals of 0.18.0 (a PASS with fewer `Evidence:` lines than ACCEPTANCE lines, a backticked path that does not exist; `cmd_check_report` 5755-5796, `evidence_lines` 4764-4767, `missing_paths` 4746-4761): the worker rewrites its file and checks again, or files it as it is when it cannot fix what the check names (worker.md "Report", step 1 -> 2; `mailbox.py report` checks only steers). Either way the row that lands is a PASS, ISSUES or BLOCKED row, which the model has; a PASS that lacks evidence is the verifier's to find. So the refusal is no state. A report that `salvage` recovers from a file or transcript is never checked (README).
- `[scope] adjacent`, the role's Method and Review text, the tier and the profile stored at launch: brief text, no state.
- `verify_mode = ci:*`, `verify_kind` other than code, `test-verified` (acts like artifact-verified for a code task), `verify-blocked` (acts like check-only), `--override-verifier`, a `--verdict` that differs from the verifier's, `--ref`, `--attempt` (the override the at-cap hint offers), `--base`, `--model`, `--dry-run`.
- Git details: a branch at another head (`branch_at`, `same_change`, `pr-changed`, `take_host_head`, `caught_up_from`), a missing or plain worktree folder, a wrong branch in it, a dirty or detached main checkout, `kept` (a `claude stop` that fails), `push-refused` and a gone remote branch. A failed first push (`push-failed`, line 4894) is in: the task is in progress with phase `awaiting_merge` and unpublished until a later close pushes.
- Tokens, report text, report file paths, transcripts: a verifier's unfiled report is one flag (`vreport`) with a passing verdict. A worker's unfiled report is left out: a salvaged PASS or ISSUES leads to the same hint as a filed one. Of a verifier's report text only two things are read: its `Verdict:` line (`vv`) and whether its `Issues:` lines carry `blocking:` (`vIssues`, 0.18.0).
- Unrecorded session rows and `record_row`: every session is recorded by the command that started it.
- The `phase` meta as a variable (0.19.0): the model reads it from `verdict` (`Closed`: only a passing close writes a passing verdict, in one edit with `phase=awaiting_merge`). Since #99 the operator `Phase` derives every phase from the model's variables, as `derive_phase` does, for the phase view (see "Phase edges"); no action or rule reads it. Left out: the backfill of a task with no phase (since 0.20.0 a done task that is merged gets no phase written; it is derived when read), a done task with an in-flight phase (a 0.18.0 close after a newer `record`; `stored_phase` reads it as no phase, so it is backfilled too), `phase-mismatch` (a hand edit), a 0.18.0 task that is done and not merged (the model starts at 0.19.0), and a command that stops between `merged_at` and `tg done` (`record_closed` and `close` finish it with `finish_merged`): the model's steps are atomic. Also left out: output outside git. A passing close records it as `phase=merged` with the verdict and marks it done at once; the model's output is always a commit. `phase-edges-exclusions.json` lists the table rows these leave without a model edge. Tests cover both: `test_crash_between_merged_at_and_done_healed`, `test_non_git_close_done_immediately` and `test_non_git_close_that_dies_in_the_stop_is_finished_by_record`.
- A verify row without a `Verdict:` line (`verified: no Verdict line`): verifier rows always carry a level. A STOPPED row without a `Reason:` line: every modelled stop writes one.
- A second verifier session's folder name and rank: one verifier row at a time; `verify --again` replaces it.
- `host-error`, `merge-failed`, `pr-draft`, `pr-unpinned`; `pr_status`'s UNKNOWN state is folded into "pending".
- A `[roles] default` that is broken refuses every launch of every task the same way as a task's own role; the model has one `fault = "role"` for both.
- `repoint` (0.21.0, #111) and what follows from it: a task that follows another task's request. See "0.21.0: repoint".

## Simplifications

1. Rows are summarised: the newest task row (`lastTask`: PASS, ISSUES, BLOCKED, BLOCKEDmgr for `file_stuck`, DIED, STOPPED without a Head line, STOPPEDhead, ABANDONED) with the `Reason:` of the newest STOPPED row (`stopReason`), `latest_worker` (`workerResult`), the newest verifier-authored verify row (`vv`), the newest Manager verify row (`vManager`: BLOCKED, or manual for `close --verdict`), their order (`vNewer`: the verifier's row is newer than the Manager's newest row *with a verdict*, which is what lines 2380-2382 read since #62), and `vfiled` (`verifier_filed`: a row covers the newest verifier session).
2. One worker and one verifier session at a time. `claude stop` is immediate except after `run.py stop`, where the row stays busy ("stopping") until the process exits, so that `commit_stopped`'s "has not exited yet" branch exists.
3. The host's answer after a push is a free choice among the open states (pending, clean, behind, blocked, dirty). Requests move: pending -> any decided state; clean or blocked -> behind; clean <-> blocked; any open -> merged or closed by someone; closed -> pending by a reopen. "behind" moves only by the host's rebase (close) or by a merge or close by hand.
4. A local merge either succeeds or conflicts (a free choice); a conflict is a decision for the operator, who can then merge by hand.
5. `HIGH_RISK = TRUE`: a PASS goes to a verifier session. With FALSE, `record_arrived` tells the Manager to rerun VERIFY itself and close with `--verdict L` (`CloseManual`), where the model lets the Manager pick any level.
6. `MAX_ATTEMPTS = 2` (the code has 3): two attempts show the retry and the cap. `AttemptBound` explores up to 3; TLC checks the rules in the states one step past it, so `TypeOK` allows 4.
7. The thirty quiet minutes are one environment step (`VerifierQuiet`). The worker has no quiet state: the code treats an idle worker the same at any age.
8. After `verify --again` the model tracks the new verifier only. In the code the old verifier's row stays; a young ghost among them refuses `launch` ("has a live session") until it comes back or goes quiet. The worker ghost shows that path; the verifier one is not drawn twice.
9. The STOP order is one boolean the operator sets and lifts (`OperatorOrdersStop`, `OperatorLiftsStop`). `cmd_stop` reads it when it runs: a stop of an idle worker while a STOP line stands is a pause, not a recovery (the owner's rule as stated, #59).
10. The no-change close (0.12.3, #72): whether the verified head holds a commit beyond its base is a free choice at close (`NoChangeClose`), only while no request exists; the model does not track the branch's commits. It records `merged` with no merge, push or request, in both modes.
11. A fault happens once per run (`faulted`), and the two faults are one variable: both refusals fire before anything is stopped or committed (the role: `choose` at 2353, `verify_role` at 2684; the exclude: 2338-2340, 2696-2698, since ff2c8b0). The read-only file is the one `info/exclude` of the repository, so launch and verify refuse together; the model has no state where one is refused and the other not.

## Rules

- `VerdictNotLost`: once the verifier's session ended or its turn ended, a verify row covers it, or record is about to write one, or record says no-verdict, or a pause is pending (a STOPPED row without a Head line: record finishes it first by design, 3744-3746, and the record after the commit finds the lost verifier). An invariant, not a liveness property: the model has no fairness (a PROPERTY would need weak fairness on `Record` and on the paused worker's exit), and a state is easier to read than a lasso.
- `NoMergeWithoutPassingVerdict`: done or merged implies the verdict meta is passing and a verify row of the attempt carries it.
- `DoneOnlyWhenMerged` (0.19.0, #97), from "A task is done only when its change is merged" (README, Task lifecycle): the status is done exactly when `merged_at` is set. `mark_merged` writes the merge and runs `tg done`; nothing else runs it on a task with a commit to merge.
- `AttemptCap` (a PROPERTY): the attempt passes MAX_ATTEMPTS only by a launch after a pause the operator ordered (the newest row is STOPPED with `Reason: pause`). The owner's rule (#59): a stop that recovers a quiet or broken session, a stop by close, and DIED all count as an attempt. As an action property it names the step that passes the cap. `refuse_past_cap` (2555-2563) is where the code keeps it.
- `PausedWipCommitted`, from "Phase 2 of a pause: commit the WIP of a stopped worker that has exited" (commit_stopped, 3673).
- `PauseFinishedFirst`, from "finish the pause first: launch needs its Head line" (record_in_progress, 3746).
- `LaunchCommitsLeftovers`, from "A dirty worktree never reaches a worker silently" (cmd_launch, 2489).
- `OneRequestPerTask`, from "Never unset pr, pr_branch, pushed or target: one request per task across attempts" (cmd_launch, 2530).
- `StoppedIdleNeverRefuses` (a PROPERTY), from "launch stops such a session itself instead of refusing" (idle_and_filed, 2323-2331): a launch that stops the idle rows and passes every other check starts the next attempt. The step must be the launch itself: the first form of the rule counted the operator's STOP order written in such a state (launch then exits 3 before it stops anything, pause.md), which broke pause.cfg, pause-pr.cfg and regress-54.cfg (an artifact of the rule, not of the code). Before part 3 of #65 the stopped idle/working row was a young ghost and the launch's second read of the live rows (2397) refused on it. Since ff2c8b0 no check but the pause and the cap follows the stops: the exclude check moved before them.
- `NoSessionLeftAtEnd`, from "Remove the sessions and worktrees of a merged task" (cleanup, 4564) and `stop_live`/`cmd_abandon` (#57): an end state leaves no live session of the task. A young ghost row at the end is not a break: `claude stop` cannot end it, it ends by itself after 30 quiet minutes, and since 0.12.1 cleanup removes it with `claude rm` once the task is done. With `REGRESS_65` it counts as left, as it was before.
- `FixRoundNeedsBlocking` (0.18.0, #89 rule 1; README "Blocking and non-blocking findings"; manager.md "No follow-up dropped": "never opens a fix round"): when a verifier's verify-failed verdict drives the next step (a fix round below the cap, abandon at it), its report has a `blocking:` line. A Manager's own `close --verdict verify-failed` is not a verifier's finding and is exempt. Since 8006a3c such a verdict is never recorded (below); `REGRESS_89` restores the old reading.
- No dead end: TLC's deadlock check, with `Done` for the end states.

## 0.18.0 refusals

What PR #87 changed in what the model reads, and what the model does with it:

- Roles are chosen at launch (`choose`, 1163-1206) and stored in the attempt's `sessions` entry (`picked.stored`, 2527). `close`, `record` and `status` read the stored kind (`verify_kind`, 2161-2176: a role problem is never refused there), so a role file that changes or goes away after the launch blocks none of them. `verify` reads the stored role's file again (`verify_role`, 1218-1225) and refuses when it is missing or broken; `launch` refuses on a broken role before the live-row scan. The model: `fault = "role"` refuses `Launch` (in `EarlyChecks`) and both verify forms (in `VerifyAccepted`); nothing else reads it. After a PASS on a high-risk task the hint is `verify` and the Manager waits for the operator's repair: by design, the refusal names the fix.
- `ignore_reports` and `ignore_scratch` (1443-1460) refuse `launch` and `verify` when `info/exclude` cannot be written. At 74aed9a they ran late: in launch after the stopped-idle stops, the worktree and a retry's WIP commit; in verify after the over verifier was stopped; in a resume after the worker's process was stopped. The model found no lost work on those paths (a stopped idle row had its work filed, the stopped verifier had no verdict) but reported the order, and ff2c8b0 moved the checks first: launch 2338-2340 (right after the STOP-order refusal), verify 2696-2698 (before the over verifier is stopped), `resume_with` 3154-3157 (before `stop_session`; a refusal is a `deliver-fallback`, the row stays pending and no try is counted). The model: `fault = "exclude"` refuses `Launch` (in `EarlyChecks`) and both verify forms (in `VerifyAccepted`), with no side effects; the refusing forms of the 74aed9a model are gone, and `StoppedIdleNeverRefuses` needs no exemption for it.

## 0.19.0

What PR-1 of #97 changed in what the model reads, and what the model does with it:

- A passing close no longer runs `tg done` (`cmd_close`, 5593-5610). The task stays `in_progress` with `phase=awaiting_merge` (written with the verdict; `merged` for output outside git), and `mark_merged` (through `finish_merged`) marks it done when the merge is recorded: `close` merging (`merge_branch`), `record` finding the request merged or merging it (`pr_status`) or the commit in `HEAD` (`record_closed`), a no-change close (`close_no_change`), and `run.py merged`. Since #99 these phase writes have no line numbers here: each one goes through `TRANSITIONS`, and the phase edges test checks the table against the model (see "Phase edges"). In the model `CloseAsPassing`, `ResumeClose`, `Record` and `Merged` set `status` to done only with `merged` (`StatusAfter`).
- `Closed` (a passing verdict) and `Awaiting` (closed, not merged, not abandoned) stand for the phase. `RecOut` sends a closed task to `RecDone` (`record_closed`), never to `RecInProgress`: its `STOPPED` row with `Reason: close` (from `stop_live`) is never committed by `commit_stopped`, and no `DIED` or `unclosed` line comes from it. `PauseFinishedFirst` therefore excludes a closed task.
- `launch`, `adopt` (`refuse_closed`, 2636-2645), `verify` and `close` (`refuse_unless_running`, 2648-2656) and `stop` (5667-5668) refuse a task that waits for its merge; `close` on it resumes (`resume_close`, 5533-5534). In the model: `EarlyChecks`, `VerifyAccepted`, `NormalClose`, `Stop`, `ResumeClose`.
- `OperatorMerges` and `Merged` need `Awaiting` instead of status done.
- `REGRESS_97` restores the old close: `tg done` at once (`StatusAfter` ignores `merged`). `regress-97.cfg` must break `DoneOnlyWhenMerged`.

The merge gate (#100, PR-4 of #97) changes no state the model has, so `Lifecycle.tla`'s logic is unchanged; only line numbers moved. A task that waits for its merge carries a Taskgraph gate `merge` (`tg gate`, taskgraph 1.19.0). It says what the task waits for and changes no status, phase or hint:

- It is set where a task starts to wait: `merge_branch` when the merge waits or conflicts (5627, 5638), `cmd_close` before `publish` in pr mode (5605-5606), and `publish` once the request is known (4862, 4865-4866, 4877; `request_gate`, 5476-5488, acts only for phase `awaiting_merge`, so a request opened by a CI verify gets none). `record_closed` writes it for a waiting task that has none (3954-3955, 3972-3973: a close that stopped before the gate, or one from before the gate existed) and keeps the request's label and URL current (3963-3964); `set_merge_gate` writes nothing when the gate already says the same, and nothing for a task that is done in Taskgraph, such as one 0.18.0 closed (5460-5468; `request_gate` asks the host nothing for it, 5480).
- It is cleared in `finish_merged` before `tg done` when the task has it (5517-5518), so every merge record clears it, and by `cmd_abandon` before the `abandoned` write (5730-5731). A command that stops between the merge record and `tg done` leaves phase `merged`, and `record_closed` finishes it: a task not done, or a done one whose gate is still there (3946-3951, `test_gate_crash_between_clear_and_done_heals`).
- On the taskgraph GitHub backend a code host can close the task's issue when the request merges ("Closes #N"). Taskgraph then reads the task as done while its phase is still `awaiting_merge`; `record_closed` follows it like a 0.18.0 task that is done and not merged, records the merge, clears the gate and runs `tg done` all the same (5519): Taskgraph keeps the task's `done_at` and, on GitHub, removes the `tg:in-progress` label the close left. `run.marked_done` lists only a task that was not done. The model starts from Taskgraph's status as run.py writes it, so it leaves this order out; `test_gate_the_host_closes_the_issue_before_record_sees_the_merge` and `test_gate_the_host_closes_first_then_record_clears_the_gate_and_runs_tg_done` cover it.

## 0.21.0: repoint

`run.py repoint <id> --pr <n>` (#111) lets a task that waits for its merge follow another task's request, which carries its change. The model leaves it out, and `Lifecycle.tla`'s logic is unchanged; only line numbers moved. Why:

- It moves no phase. The task stays `awaiting_merge`, `TRANSITIONS` has no row for it, and `phase-edges.json` is unchanged.
- Its state is outside the model. The model checks one task and its own request (`pr`). A task that follows a request another task owns, and that request merging with or without the task's commit, needs two tasks and two requests.
- No modelled step changes for a task that is not repointed. Each new branch tests `repointed` (the `repointed_at` meta) first, and only repoint writes it: `record_closed` sends a repointed task to `follow_request` instead of `pr_status` (`Record`); `cmd_close` refuses a repointed task before `resume_close` (`ResumeClose`); `cmd_launch` moves the `repointed_*` keys back to `pr`, `pr_branch` and `pushed` (`Launch` after `Abandon`); `cmd_abandon` names the followed request in its line (`Abandon`); `not_merged_reason` counts the verified commit of a repointed task as merged (cleanup, out of scope).
- `OneRequestPerTask` is about the task's own request, which the model's `pr` stands for. repoint keeps it in `repointed_from` and the next launch puts it back, so the task's own request is never dropped. The one case where the `pr` meta goes from set to unset is a task repointed before it had a request of its own: its own request was none before and is none again.
- The hints a repointed task gets (`pr-closed` with `run.py repoint`, the `close` refusal) name `repoint`, `abandon` and `launch --attempt`; `follows` and `target-check` name nothing. None of them is a hint of a state the model has.
- The merge of the followed request completes the task (#111, Decision): `follow_request` runs `mark_merged` with `merged_by=repoint` and `merged_via=<n>`, whatever `in_target` says (its `target-check` line is information). So a repointed task that waits has no state with no step out: the request merges (done) or closes (`pr-closed`, repoint or abandon). `DoneOnlyWhenMerged` and `NoMergeWithoutPassingVerdict` would still hold: the merge goes through `mark_merged`, and only a passing close leaves a task `awaiting_merge`. The repoint, like `run.py merged --by operator`, is the operator's word that the change went in.

Tests cover it in `tests/test_run.py` (`RepointTest`, the `test_111_*` tests) and `tests/test_host.py` (`test_111_close_pr_*`).

## Phase edges (#99)

`run.py` changes the `phase` meta only through its table `TRANSITIONS`: `(phase, event) -> phase`. `test_the_table_has_the_edges_of_the_model` in `tests/test_run.py` checks that the table and the model have the same edges. It needs no TLC:

- `Phase` in `Lifecycle.tla` is the model's reading of `derive_phase`: abandoned, merged, not started (`"none"`, the code's None), the verdict (awaiting_merge or verdict_failed), then the newest task row: none (running), not a worker result (stopped), a worker result with a verifier or a verify row (verifying), else reported. No action or rule reads it, so the states and the rules are unchanged.
- `phase-view.mjs` draws each state as its phase. Its `state()` is `Phase` in JavaScript, so change the two together. It labels each step with run.py's event name: `Launch` is launch, `VerifyPlain` and `VerifyAgain` verify, a close close_failed or close_waits, or `close_waits, merged` when it merges at once (run.py writes twice: the close, then `mark_merged`), or merged when it resumes a waiting task and merges. `Stop` is stopped, `Abandon` abandon, `Merged` merged. `Record` is merged for a merge it records, died for DIED, and stopped for `file_stuck`. Every environment step is `seen_<phase>`: the world moved, and the next `record`'s `settle_phase` sees what the rows say. A step that keeps the phase is dropped. A `Record` step that moves the phase in any other way is labelled `record`, and the test fails on that name. Its labels are run.py's names on purpose, so the statechart command's label warnings (short labels, no actor) are expected for this view; it is a maintainer's check, not a chart for the README.
- `phase-edges.json` holds the edges of `check.cfg` and `check-pr.cfg` together: 18 edges. Once each `close_waits, merged` is split, they are 16 table rows. The test walks a two-event edge through the table.
- `phase-edges-exclusions.json` says why the two sides differ, one `[from, event, to]` pattern and one reason per entry. The first entry that matches an edge explains it. The test fails on an edge that no entry explains, and on an entry that explains no edge. Every model edge is a table row today (`model` is empty). The table rows with no model edge are: the backfill, output outside git, adopt, the crash heal, hand edits, `file_died`, a verify row with no `run.py verify`, the operator's own commands (abandon or a pause where no hint says so, `launch --attempt`), rows that keep the phase (the view cannot show them), and commands whose guard accepts a phase that no hint leads to (verify or close before `record` saw the report, launch before a verdict is closed).
- `Phase` is derived, so after a failed verdict `verify --again` keeps `verdict_failed` in the model while run.py writes `verifying`; `settle_phase` allows that pair. The model's close that follows starts from `verdict_failed`. The table has that row too (a close with `--override-verifier`).

The fixture was first written by hand from the actions, in a session that could not run TLC. Regenerate it from TLC's state graph. The statechart command draws no chart above 500 states, and `check.cfg` has about 15,500, so `phase-edges.mjs` reads TLC's own graph dump with the statechart skill's parser and the phase view:

```
cd plugins/agentic-team/model
OUT=<a new folder outside the repository>
"$JAVA" -XX:+UseParallelGC -cp "$TLA2TOOLS" tlc2.TLC -config check.cfg -dump dot,actionlabels "$OUT/check" -metadir "$OUT/states-check" Lifecycle.tla
"$JAVA" -XX:+UseParallelGC -cp "$TLA2TOOLS" tlc2.TLC -config check-pr.cfg -dump dot,actionlabels "$OUT/check-pr" -metadir "$OUT/states-check-pr" Lifecycle.tla
node phase-edges.mjs "$OUT/check.dot" "$OUT/check-pr.dot" > phase-edges.json
git diff --exit-code phase-edges.json
```

`phase-edges.mjs` needs a Node that runs TypeScript, the same one the statechart command needs. The diff must be empty, or explained in PREDICTIONS.md and in the exclusions. To see the phases of the main flow as a chart, run the statechart command with `--config overview.cfg --view phase-view.mjs`, which stays under the budget.

What the test covers: which phase changes exist, from which phase, and by which event, in both the code and the model. What it does not cover: how a command decides (its refusals, its hints, and the rows and meta it writes beside the phase), and what the model's actions read. Those keep their line numbers in the action table, in `Lifecycle.tla` and in this file, and still need updating by hand when run.py moves (see "Keeping the model current"). The line numbers that only pointed at a phase write are gone (from "0.19.0" and "What the model leaves out"). `Lifecycle.tla` had no such line number: each of its line numbers points at a hint, a guard or a field that the model reads.

## Ghost rows (#65)

What 0.12.1 changes, and what the model does with it:

- The session cap (`live_count`, 652-653, no longer counts ghosts) is out of the model's scope: the cap is a count across every task on the machine, and the model checks one task. `check_cap` is left out (above).
- `cleanup` (4564-4664) is out of the model's scope too, as before. The ghost part of cleanup (a ghost is removable and does not keep its folder) is reflected in one rule: `NoSessionLeftAtEnd` lets a ghost row stand at the end, because cleanup removes it then; `REGRESS_65` makes it count as left, and `regress-65.cfg` must break.
- `merged_into` accepting a rebased commit (`git cherry`, 4278-4290) changes no modelled decision: `mainHas` already stands for "the main checkout holds the change".
- What the model does check: a ghost worker or verifier of a task in progress. Part 1 alone left a dead end, which the model found: a ghost row that holds a result or a stop blocked `launch` for ever (`idle_and_filed` needs a status, a ghost has none; `claude stop` does not change the row; no hint names `claude rm`). Part 2 ends the row after 30 quiet minutes (`quiet_for`, `Run.sessions`), so the young ghost either comes back or ends, and every path goes on: launch does not refuse on an ended row, record salvages or files DIED, a verifier goes to `no-verdict`. `REGRESS_65` restores a ghost that never ends (and cleanup that skips it): `regress-65.cfg` must break NoDeadlock on that path (and, before part 3, NoSessionLeftAtEnd on a ghost left at the end).
- The 2026-11-05 probe showed that a session does not come back after `claude stop` ran on its ghost; the 2026-11-06 probe showed what the stop leaves (state kept, status and pid removed). With part 3 a run.py stop ends the row at once, whatever it was. No dead end remains in the model.
- A stopped `blocked` row (an idleBlocked session stopped before part 3) would read as live and stuck, not as a ghost; the model does not draw that pre-part-3 variant, since part 3 ends it like every other noted row.

## Keeping the model current

When `run.py` changes a hint, a refusal, or what a command writes, change the matching action and its line numbers, run `check.cfg`, the regress configs and `pause.cfg`, and update PREDICTIONS.md. When it changes `TRANSITIONS`, or a change to the model moves a phase, regenerate `phase-edges.json` ("Phase edges") and run the test; a new difference gets an exclusion with its reason, or a fix. When the check finds a new break, confirm it in the code at the line, file it, and give it an `ALLOW_*` switch (TRUE: the real way out) until the fix lands; then turn the switch into a `REGRESS_*` constant and a regress config.
